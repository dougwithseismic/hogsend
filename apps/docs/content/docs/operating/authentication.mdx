Hogsend has **two authentication surfaces**:

- **Studio login** — the human path. A logged-in operator using the [Studio](/docs/operating/studio) admin UI, authed by a Better Auth session cookie. Public sign-up is disabled; the first admin is minted from your server (see [Studio admin login](#studio-admin-login) below).
- **API keys** — the machine path. Bearer tokens in the `Authorization` header for the CLI, CI, agents, and your own app code. This is the bulk of the page below.

API keys guard two planes: the **admin/ops plane** (`/v1/admin/*`) and the public **data plane** (`/v1/contacts`, `/v1/events`, `/v1/emails`, `/v1/lists` — see the [Data API](/docs/data-api/authentication)). Hogsend supports two key modes — a legacy environment-variable key for quick setup, and database-backed keys with scoped permissions for production use. Database-backed keys come in two classes: **secret** (`hsk_`, server-side) and **publishable** (`pk_`, browser code, Origin-checked). The difference is covered in [Data API: Secret and publishable keys](/docs/data-api/authentication#secret-and-publishable-keys).

<Callout type="info">
  Both planes are bearer-authed, but the data plane is **not** under `/v1/admin`. A key reaches the data plane only via the `ingest` scope (or `full-admin`), and an `ingest`-only key reaches nothing on `/v1/admin/*`. See [Key Scopes](#key-scopes) below for why `ingest` is orthogonal, not hierarchical.
</Callout>

## Studio admin login

The Studio is authed by a Better Auth session, not an API key. **Public web sign-up is disabled at the auth layer** — `createAuth()` sets `emailAndPassword: { enabled: true, disableSignUp: true, minPasswordLength: 8, maxPasswordLength: 128 }`. There is **no unauthenticated network path that creates any user or admin**: `POST /api/auth/sign-up/email` returns `400 EMAIL_PASSWORD_SIGN_UP_DISABLED` for everyone, and so does the in-process `auth.api.signUpEmail` (the `disableSignUp` check lives inside the sign-up handler in better-auth 1.6.11). There is **no setup token and no web create-admin form** — both are gone.

Public sign-up is disabled, so the first Studio admin is created from your server — run `hogsend studio admin create` (it needs `DATABASE_URL` + `BETTER_AUTH_SECRET` + shell access), or set `STUDIO_ADMIN_EMAIL` (+ optional `STUDIO_ADMIN_PASSWORD`) and the API mints it on boot into an empty user table:

```bash
# CLI — DB-direct, no HTTP, no running API; env must be loaded
dotenvx run -- hogsend studio admin create --email admin@example.com
railway run hogsend studio admin create --email admin@example.com
pnpm studio:admin                                # scaffold wrapper, loads .env

# Env bootstrap — set on the deploy; mints on a zero-user DB at boot
STUDIO_ADMIN_EMAIL=admin@example.com
STUDIO_ADMIN_PASSWORD=...                         # optional; omit and one is auto-generated + printed once
```

Web Studio is **login + self-service forgot/reset only**. A zero-users instance renders a read-only info screen (no inputs, no network create path) pointing at `hogsend studio admin create` / `STUDIO_ADMIN_*`. Self-service reset uses Better Auth's `/request-password-reset` + `/reset-password` (single-use token, 15-minute TTL, sessions revoked on reset); it is live only when an email provider is configured. Locked out with no email provider? Recover with `hogsend studio admin reset`. The full first-admin and recovery story lives in the [Studio](/docs/operating/studio#first-load-create-the-first-admin) and [`hogsend studio admin`](/docs/cli/studio) pages.

<Callout type="warn">
  **Redis is required for auth in production.** `createHogsendClient` wires Better Auth's `secondaryStorage` to the shared engine Redis — it holds sessions, reset tokens, and rate-limit counters — gated on a raw `REDIS_URL` being set. With it, the sign-in (`10/60s`) and password-reset (`5/60s`) rate limiters are **global across replicas** and survive restarts; without it they are per-instance and lost on restart. Set `REDIS_URL` in production.
</Callout>

## How Auth Works

When a request hits any `/v1/admin/*` endpoint, the auth middleware runs this sequence:

1. Extract the `Authorization: Bearer <token>` header
2. Check if the token matches the `ADMIN_API_KEY` environment variable (legacy key, full access)
3. If no match, SHA-256 hash the token and look it up in the `apiKeys` database table
4. Verify the key is not revoked and not expired
5. Check that the key's scopes permit the requested operation. A bearer request to any admin route requires `full-admin`; the data-plane routes require the orthogonal `ingest` scope instead (see [Key Scopes](#key-scopes))
6. If neither mode matches, return `401 Unauthorized`

If no admin key is configured at all (no `ADMIN_API_KEY` env var, no database keys), admin endpoints return `503 Service Unavailable`.

Active keys, secret and publishable, are cached in memory for 60 seconds per API instance. A newly created key works immediately (cache miss triggers a DB lookup). Revoking or rotating a key evicts its entry on the instance that served the request; other instances may accept it for up to 60 seconds until their entry expires.

## Legacy Key (Quick Start)

Set the `ADMIN_API_KEY` environment variable and you are ready to go:

```bash
# .env
ADMIN_API_KEY=hsk_your-secret-admin-key-at-least-32-chars
```

```bash
curl -H "Authorization: Bearer hsk_your-secret-admin-key-at-least-32-chars" \
  http://localhost:3002/v1/admin/contacts
```

The legacy key always has full admin access -- it can perform any operation. This is fine for local development and single-operator setups, but for production you should create scoped keys.

## Creating Your First Database-Backed Key

Use the legacy key (or any existing `full-admin` key) to create a new scoped key:

```bash
curl -X POST http://localhost:3002/v1/admin/api-keys \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Deploy pipeline",
    "scopes": ["full-admin"],
    "expiresAt": "2026-12-31T00:00:00.000Z"
  }'
```

```json
{
  "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "name": "Deploy pipeline",
  "key": "hsk_abc123def456ghi789jkl012mno345pqr678",
  "keyPrefix": "hsk_abc1",
  "scopes": ["full-admin"],
  "allowedOrigins": null,
  "expiresAt": "2026-12-31T00:00:00.000Z",
  "createdAt": "2026-01-15T10:30:00.000Z"
}
```

**Save the `key` value immediately.** It is SHA-256 hashed before storage and will never be shown again. If you lose it, revoke the key and create a new one.

The `keyPrefix` field (first 8 characters) is stored in plaintext so you can identify keys in list views without exposing the full token.

## Key Scopes

Each database-backed key has one or more scopes that control what it can do. There are **two kinds** of scope:

| Scope | Kind | What it allows |
|---|---|---|
| `read` | hierarchical | Reserved. Accepted at mint time, but no admin route grants anything to it over a bearer key today |
| `journey-admin` | hierarchical | Reserved, like `read` |
| `full-admin` | hierarchical | The whole admin plane (`/v1/admin/*`) -- metrics, contacts, journeys, key management, bulk imports/exports, alerts, event replay, email resend. **Also implies every orthogonal scope** |
| `ingest` | **orthogonal** | The public data plane -- write `/v1/contacts`, `/v1/events`, `/v1/emails`, `/v1/lists`. Grants **nothing** on `/v1/admin/*` |
| `accounts` | **orthogonal** | The [account-link](/docs/guides/account-links) operator routes (`/v1/accounts` lookup, unlink, import, mint-link) |
| `referrals` | **orthogonal** | The [referral](/docs/guides/referrals) report, tree, touch and import routes |
| `ingest-public` | **orthogonal** | Publishable (`pk_`) keys only, set by `publishable: true`. The browser-reachable ingest routes, Origin-checked |

The three admin scopes are **hierarchical and cumulative** -- a key with `["journey-admin"]` implicitly has `read`. Today a bearer request to `/v1/admin/*` requires `full-admin`, so `read` and `journey-admin` keys reach nothing there; mint `full-admin` for admin access.

`ingest`, `accounts`, `referrals` and `ingest-public` are different: they are **orthogonal, not hierarchical**, and sit entirely outside the `read < journey-admin < full-admin` ladder.

<Callout type="warn">
  A `read` or `journey-admin` key does **NOT** get `ingest`. Holding an admin tier grants nothing on the data plane. A key reaches the data plane only with an explicit `ingest` grant or `full-admin` (which implies it). Conversely, an `ingest`-only key reaches nothing on `/v1/admin/*`. Combine them (e.g. `["read", "ingest"]`) when a single key needs both planes.
</Callout>

This is enforced by `hasScope()` in the engine's `middleware/api-key.ts`: a required orthogonal scope (`ingest`) is satisfied only by `keyScopes.includes("ingest") || keyScopes.includes("full-admin")` — never by a hierarchical rank. The full data-plane key story lives in the [Data API authentication](/docs/data-api/authentication) page.

### Which scope do I need?

| Task | Credential |
|---|---|
| Anything on `/v1/admin/*` (metrics, contacts, journeys, email history, imports/exports, alerts, replay, resend, DLQ, key management) | `full-admin` key, or a Studio session |
| Write contacts/events/emails/lists from your backend | `ingest` key |
| Look up, unlink or import linked accounts | `accounts` key |
| Read referral reports and trees, record touches, import edges | `referrals` key |
| Capture events, read the feed or flags, manage preferences from a browser | publishable key (`ingest-public`) |

A request with insufficient scope returns `403 Forbidden`:

```json
{ "error": "Forbidden: insufficient scope" }
```

## Key Lifecycle

### Create

```bash
curl -X POST http://localhost:3002/v1/admin/api-keys \
  -H "Authorization: Bearer your-api-key" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Backend (production)",
    "scopes": ["ingest"],
    "expiresAt": "2027-06-01T00:00:00.000Z"
  }'
```

The `name` field is for your reference -- use it to identify what the key is for when reviewing the key list or audit logs. The `expiresAt` field is optional; keys without an expiry date are valid until revoked. For a browser key, pass `"publishable": true` and a non-empty `allowedOrigins` list instead of `scopes` (see [Minting a publishable key](/docs/data-api/authentication#minting-a-publishable-key)).

### Use

Include the key as a bearer token in the `Authorization` header:

```bash
curl -H "Authorization: Bearer hsk_abc123def456ghi789..." \
  http://localhost:3002/v1/admin/contacts
```

The `lastUsedAt` timestamp on the key record updates when the key is used, so you can identify stale keys that should be cleaned up.

### List

```bash
curl -H "Authorization: Bearer your-api-key" \
  http://localhost:3002/v1/admin/api-keys
```

Revoked keys are hidden by default. To see them:

```bash
curl -H "Authorization: Bearer your-api-key" \
  "http://localhost:3002/v1/admin/api-keys?includeRevoked=true"
```

### Rotate

`POST /v1/admin/api-keys/:id/rotate` (requires `full-admin`) mints a replacement key with the same name, scopes, key class (secret or publishable) and `allowedOrigins`, and sets the old key to expire after a grace period. Both keys work until the grace period ends, so running deployments keep working while you roll the new key out.

```bash
curl -X POST http://localhost:3002/v1/admin/api-keys/a1b2c3d4-e5f6-7890-abcd-ef1234567890/rotate \
  -H "Authorization: Bearer your-api-key" \
  -H "Content-Type: application/json" \
  -d '{ "gracePeriodSeconds": 3600 }'
```

```json
{
  "id": "f0e1d2c3-b4a5-4678-9abc-def012345678",
  "name": "Backend (production)",
  "key": "hsk_newkey456def789ghi012jkl345mno678pqr",
  "keyPrefix": "hsk_newk",
  "scopes": ["ingest"],
  "allowedOrigins": null,
  "expiresAt": null,
  "createdAt": "2026-03-01T09:00:00.000Z",
  "rotatedFrom": {
    "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "expiresAt": "2026-03-01T10:00:00.000Z"
  }
}
```

The body is optional:

| Field | Default | Meaning |
|---|---|---|
| `gracePeriodSeconds` | `86400` (24 hours) | How long the old key keeps working, `0` to `2592000` (30 days). `0` retires it immediately |
| `expiresAt` | none | ISO 8601 expiry for the new key. Omit for a key that is valid until revoked |

Rotation never extends the old key's life: if it already expires before the grace period would end, that earlier expiry stands. The new `key` is shown once, like on create. Rotating an unknown or revoked key returns `404`.

The procedure:

1. Rotate the key and save the new `key` value from the response.
2. Deploy the new key to every system that uses the old one (env vars, CI secrets, the front-end config for a publishable key) before `rotatedFrom.expiresAt`.
3. Check the old key's `lastUsedAt` in `GET /v1/admin/api-keys`. Once it stops moving, nothing is using it.
4. Let it expire, or revoke it early with `DELETE /v1/admin/api-keys/:id`.

If a key has leaked, rotate with `"gracePeriodSeconds": 0`, then deploy the new key. The old key stops working at once on the instance that handled the rotation and within 60 seconds on the others (the auth cache TTL). This applies to publishable keys too.

The API keys section of Studio settings lists, creates and revokes keys; rotation is API-only for now.

The legacy `ADMIN_API_KEY` is not a database row, so it has no rotate endpoint and no grace period. To rotate it, mint a `full-admin` database key first, move your tooling to that key, then change `ADMIN_API_KEY` on the API service and redeploy (or unset it to retire the legacy key).

### Revoke

```bash
curl -X DELETE http://localhost:3002/v1/admin/api-keys/key-uuid \
  -H "Authorization: Bearer your-api-key"
```

Revocation sets `revokedAt` on the key record and evicts the key's in-memory cache entry on the instance that served the request, so the key is refused there at once. Other API instances keep their cached entry for up to 60 seconds, for publishable and secret keys alike.

## Best Practices

**Give application code an `ingest` key.** Your backend writes the data plane; it does not need `full-admin`. An `ingest` key that leaks can write events and contacts but cannot read your data or mint keys.

**Use a publishable key in the browser, never a secret key.** Anything in front-end JavaScript is public. A `pk_` key is built for that: it reaches only the browser-reachable routes, from the origins you list.

**Reserve `full-admin` for operators.** Only human operators and trusted automation (like your deploy pipeline) should have `full-admin` keys.

**Use one key per service or site.** Separate keys get separate rate-limit budgets, show up separately in `lastUsedAt` and audit logs, and can be rotated or revoked one at a time.

**Rotate on a schedule.** Set an expiry on CI/CD keys (90 days is common) and rotate them with `POST /v1/admin/api-keys/:id/rotate` before they lapse; the grace period covers the deploy.

**Use short-lived keys for one-off tasks.** Running a data migration? Create a `full-admin` key with a 24-hour expiry. It auto-expires when you are done.

**Name keys descriptively.** The name appears in audit logs. "CI Pipeline" or "Marketing site (browser)" is much more useful than "key1" when you are investigating an incident.

**Audit key usage periodically.** List your keys and check `lastUsedAt` -- revoke any key that has not been used in months.

## Rate Limiting

Each plane has its own sliding-window limits, Redis-backed with an in-memory (per-instance) fallback:

| Surface | Bucket | Default | Configure with |
|---|---|---|---|
| `/v1/admin/*` | per key (or Studio user) | 100 per 60s | fixed |
| Browser-reachable ingest routes, secret key | per key | 3000 per 60s | `INGEST_RATE_LIMIT_MAX` |
| Browser-reachable ingest routes, publishable key | per key, per client IP | 1000 per 60s | `INGEST_PUBLIC_RATE_LIMIT_MAX` |
| `/v1/emails` | per key | 30 per 60s | `EMAIL_RATE_LIMIT_MAX` |

`INGEST_RATE_LIMIT_WINDOW_MS` (default `60000`) sets the window for both ingest budgets. The legacy `ADMIN_API_KEY` is one key, so every caller using it shares one admin budget. Which routes count as browser-reachable, why the publishable budget is per IP, and how the SDKs react to a `429` are covered in [Data API: Rate limits](/docs/data-api/authentication#rate-limits).

The Studio auth endpoints have their own Better Auth limiters on top of this — `/sign-in/email` at `10/60s` and `/request-password-reset` at `5/60s`. Those counters live in the shared Redis `secondaryStorage`, so they are global across replicas (set `REDIS_URL` in production — see [Studio admin login](#studio-admin-login)).

Every rate-limited response carries these headers, and CORS exposes them to browser code:

| Header | Description |
|---|---|
| `RateLimit-Limit` | Requests allowed per window |
| `RateLimit-Remaining` | Requests remaining in the current window |
| `RateLimit-Reset` | Seconds until the window frees a slot |
| `RateLimit-Policy` | `<limit>;w=<window seconds>`, e.g. `100;w=60` |
| `X-RateLimit-Limit`, `X-RateLimit-Remaining` | The same values under the older names |
| `Retry-After` | Seconds until the next request is accepted (only on 429) |

When the limit is exceeded:

```
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 32
RateLimit-Policy: 100;w=60
Retry-After: 32
```

```json
{ "error": "Rate limit exceeded" }
```

A rejected request still counts toward the window, so wait the full `Retry-After` before retrying. To stay under the admin limit: use bulk endpoints (`/import`, `/enroll/batch`, `/replay`) instead of looping individual calls, and cache read responses client-side when possible.

## Troubleshooting

### 401 Unauthorized

The token is missing, malformed, or does not match any known key.

- Verify the `Authorization` header format: `Bearer <token>` (note the space)
- Check that the key has not been revoked (`GET /v1/admin/api-keys?includeRevoked=true`)
- Check that the key has not expired. A key rotated out with a grace period expires at `rotatedFrom.expiresAt`
- If using the legacy key, verify `ADMIN_API_KEY` is set in your environment

### 403 Forbidden

The key is valid but does not have the required scope for this operation.

- Check the key's scopes (`GET /v1/admin/api-keys`)
- Every `/v1/admin/*` route requires `full-admin` over a bearer key
- Data-plane routes require `ingest` (or `full-admin`); a `read` or `journey-admin` key gets nothing there
- For a publishable key, `{ "error": "Forbidden: origin not allowed" }` means the request's `Origin` is missing or not an exact match for an `allowedOrigins` entry

### 429 Too Many Requests

You have exceeded a rate limit. The `RateLimit-Policy` header tells you which budget (`100;w=60` is the admin plane).

- Wait for the `Retry-After` header's seconds before retrying
- Use bulk endpoints instead of individual calls
- Use a separate key per service so each gets its own budget
- For the data-plane budgets, raise `INGEST_RATE_LIMIT_MAX`, `INGEST_PUBLIC_RATE_LIMIT_MAX` or `EMAIL_RATE_LIMIT_MAX` on the API service

### 503 Service Unavailable

No authentication method is configured. The API cannot accept admin requests.

- Set the `ADMIN_API_KEY` environment variable, or
- Create at least one database-backed key (requires the legacy key to bootstrap)

For the full endpoint specification of key management endpoints, see the [API Reference](/docs/api).

## Production Security Checklist

When deploying Hogsend to production:

1. **Set a strong `ADMIN_API_KEY`** — at least 32 random characters
2. **Set a strong `BETTER_AUTH_SECRET`** — used for session signing and reset-token derivation
3. **Provision Redis and set `REDIS_URL`** — required for sessions, reset tokens, and cross-replica auth and API rate limiting
4. **Mint the first Studio admin from your server** — `hogsend studio admin create` or `STUDIO_ADMIN_EMAIL`; never expose a create path over HTTP
5. **Use HTTPS** — all API keys and session cookies are transmitted in headers; never use HTTP in production
6. **Create scoped keys** — avoid sharing the legacy key; give application code `ingest` keys and browser code publishable keys
7. **Set key expiry dates** — especially for CI/CD and one-time migration keys, and rotate before they lapse
8. **Monitor audit logs** — periodically review for unexpected mutations
9. **Configure email webhook verification** — set your provider's webhook secret (`RESEND_WEBHOOK_SECRET` for the default Resend provider; Postmark uses HTTP Basic creds via `POSTMARK_WEBHOOK_USER`/`POSTMARK_WEBHOOK_PASS`) to validate inbound delivery events
10. **Review rate limit settings** — the defaults (3000/min per secret key, 1000/min per publishable key per IP, 30 emails/min per key) suit most apps; adjust with `INGEST_RATE_LIMIT_MAX`, `INGEST_PUBLIC_RATE_LIMIT_MAX` and `EMAIL_RATE_LIMIT_MAX`
